# v3.8.6 — 路由层高优先级代码修复

**日期**：2026-07-23  
**类型**：修复 (fix) — 4 项代码逻辑问题  
**影响范围**：`00_核心主体/脑.py` — `_route_intent()`、关键词降级分支、`_try_ollama()`

## 修复清单

### DC3 — 硬编码 Ollama 主机地址

**问题**：`_try_ollama()` 内部函数硬编码 `http://127.0.0.1:11434/api/generate`，忽略 `模型.json` 中的 `ollama_host` 配置。如果用户设置了自定义 Host（如 WSL 通过 Windows 宿主 IP 访问），路由请求会静默失败。

**修复**：读取模块级 `OLLAMA_HOST` 变量（从 `模型.json` 加载），优先使用配置值，配置为空时退回 `http://127.0.0.1:11434`。

```python
# 旧
req = urllib.request.Request("http://127.0.0.1:11434/api/generate", ...)

# 新
host = OLLAMA_HOST if OLLAMA_HOST else "http://127.0.0.1:11434"
url = f"{host.rstrip('/')}/api/generate"
req = urllib.request.Request(url, ...)
```

### DC4 — 永不触达的 dead branch

**问题**：`if action == "ask_clarify" and parsed.get("message")` 分支永远无法执行。`ask_clarify` 是 tool 名称，不是 action 名称（action 始终是 `delete_scope`）。且 LLM 输出格式中 message 嵌套在 `params` 内，不在顶层。

**修复**：移除该 dead branch（2 行）。

### DC2 — 不可达的 elif 分支

**问题**：关键词降级逻辑中有两个 `elif any(kw in DELETE_KW)` 分支。第一个在 L845 已捕获所有删除关键词匹配（通过 if/elif 链的早期拦截），第二个在 L889 永远无法执行。

**修复**：移除不可达的第二个 `elif any(kw in DELETE_KW)` 块（5 行）。关键词降级链现在按正确顺序：DELETE_KW → FINANCE_KW → CORRECTION_KW → SCHEDULE_KW → 聊天。

### L1 — ask_clarify 的 null params 处理

**问题**：当 LLM 生成 `{"tool":"ask_clarify","params":null}` 时（如"财务无金额"路径），`_parse_result` 中的 `isinstance(params, dict)` 检查导致默认值回调被跳过。虽然 handler (`if tool == "ask_clarify":`) 使用 `intent.get("params", {})` 可以安全降级，但 `target_type` 错误地默认到 `"schedule"` 而非适当的上下文类型。

**修复**：将 parser 中的 `isinstance(params, dict)` 守卫改为无条件设置默认值：

```python
# 旧
if isinstance(params, dict):
    params.setdefault("target_type", "schedule")
    ...

# 新
if not isinstance(params, dict):
    params = {}
params.setdefault("target_type", "schedule")
...
```
